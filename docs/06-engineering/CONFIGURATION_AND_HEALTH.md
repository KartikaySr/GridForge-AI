# Configuration and health conventions

## Native runtime through Phase 2

The native host creates the runtime session. There is no environment or UI switch for live
control, no default credential, and no user-supplied runtime URL. Python receives protocol=1,
a fresh random credential and instance UUID through a private stdin pipe. It binds an ephemeral
127.0.0.1 port and reports readiness through stdout after startup. Only the native host sees the
credential. A restart invalidates the old session. Details are in ADR 0002.

The runtime exposes authenticated GET /api/v1/system/health and
GET /api/v1/system/diagnostics. Both use no-store responses and a generated X-Request-ID.
Unauthorized requests return structured LOCAL_AUTH_REQUIRED errors. Browser origins are denied.
There is no public OpenAPI/docs endpoint. Authenticated telemetry ingestion, history, SSE and
simulation-only scenario routes are described in API_EVENT_CONTRACTS.md.

Health identifies mode=SIMULATION, readiness_scope=telemetry and operational_ready=false.
It includes instance identity, UTC start/observation times, uptime and explicit component states.
A generated synthetic facility identity persists in SQLite; cloud is not configured.
The host supplies .local/edge.db through the private bootstrap pipe. Tests may use ephemeral stores.
A successful HTTP response is evidence of shell readiness, never physical-control readiness.

Native lifecycle states are STARTING, READY, DEGRADED, FAILED, STOPPING, STOPPED and RESTARTING.
Browser preview uses UNAVAILABLE. UI health older than five seconds is STALE. Native calls have
bounded HTTP timeouts and the frontend adds a 2.5-second IPC timeout. Polls do not overlap.
Three failed native health checks stop the child; an operator can restart it explicitly.

Diagnostics include allowlisted runtime health/log fields, native lifecycle state and synthetic
telemetry snapshots. Telemetry identity and measurements are intentional diagnostic content.
No headers, bodies, user-supplied paths, environment variables, bearer credentials or raw
exception strings are copied into reports. Python request logs are bounded to 100 records and
report discarded counts. Native lifecycle history is bounded to 64 entries. Both reset with their
own process and are not substitutes for the later durable audit system.

Display preferences use versioned localStorage for theme/density only. Storage failure is visible
and leaves a session-only preference. Facility identity, permissions and policies are not local
presentation preferences. Persistent user credentials are deferred and must use OS facilities.

## Legacy Phase 0 and optional database configuration

The root .env.example applies to the separately launched legacy API/simulator and optional
PostgreSQL container. It does not configure the native runtime or grant operational authority.
GRIDFORGE_MODE remains SIMULATION-only on the legacy API. GRIDFORGE_CORS_ORIGINS accepts
explicit loopback HTTP origins. GRIDFORGE_TELEMETRY_URL is loopback-only. VITE_API_URL is used
only by the unmounted legacy transport. POSTGRES_USER, POSTGRES_DB and POSTGRES_PASSWORD
configure the optional local container. VITE-prefixed variables are public; never store secrets.

Legacy Python processes use their environment (or uv run --env-file .env); they do not silently
read .env. The legacy /health endpoint is liveness only and remains separate from native health.
The legacy API is unauthenticated and must not be exposed. Native startup does not mount it.

## Phase 8 optional cloud sync configuration

The native runtime reads `GRIDFORGE_CLOUD_URL` and `GRIDFORGE_EDGE_TOKEN` from its process
environment. It does not load `.env`. The cloud receiver reads
`GRIDFORGE_CLOUD_DATABASE_URL` and optional `GRIDFORGE_CLOUD_PORT` from its own environment.
The token is generated by administrator enrollment and stored in a mode-0600 file; the edge
process consumes it from the environment. Never put it in a Vite variable, URL, log or source.
Non-loopback cloud URLs must use HTTPS; local loopback HTTP is development-only. Production
credential storage in OS facilities, rotation and full cloud identity administration remain
future work.

Without both edge settings, health reports cloud/sync NOT_CONFIGURED. With settings but no
receiver, cloud is OFFLINE, sync is PENDING, and all local work continues. On successful upload,
cloud becomes CONNECTED and sync is SYNCHRONIZED only when no event remains pending. Sequence,
scope or replay conflicts quarantine that stream and show CONFLICT; other streams can continue.
Sync Center reports pending count, oldest age, last acknowledgement and per-stream cursors.
`operational_ready` stays false because cloud connectivity grants no machine authority.

## Subsequent phases

Operational state must include source, quality and freshness; permission and facility scope
remain server-authoritative. Add dependency-specific readiness as storage/workers are implemented.
Use code/message/details/request_id errors and safe structured logs. Carry correlation/causation
IDs through the full decision chain. Missing tariff, bad telemetry, missing authorization or
unavailable durable storage must never produce fabricated operational success.

## Phase 3 registry and OT diagnostics

Configuration is durable and server scoped. Registry writes use expected revision and request
idempotency UUIDs; metadata and ConfigurationChanged events commit together. Unknown references,
disabled parents, inconsistent asset bounds and unsupported protocols are rejected. The native
host exposes only registry_read/registry_save IPC, with bounded requests/responses.

The OT Devices screen distinguishes connector enabled state, connectivity, receipt freshness,
quality and mapping count. This health describes a read-only synthetic adapter, never OT safety
readiness. Facility timezone affects telemetry presentation. Capability/flexibility and maintenance
fields are metadata only; operational_ready remains false. See ADR 0004 for limits and semantics.

## Phase 4 forecast/risk additions

Facility registry now accepts optional simulation_demand_threshold_kw. It defaults to absent,
has no safety/utility-contract meaning, and follows normal revision/idempotency/audit rules.
Clearing it produces UNKNOWN risk. All facility revision changes supersede prior open risks.

The forecast-risk health component reports worker availability, not data readiness or accuracy.
Forecasting & Risk separately shows quality reasons, current assessment, persisted source/model
evidence and evaluation. A healthy worker can legitimately have no usable forecast during warm-up.
The fixed baseline assumes 1 Hz active-power telemetry, five past minute bins with at least 80%
distinct-second coverage per asset, and a 30-minute horizon. These are versioned model parameters,
not site safety limits. No environment variable silently changes the registered model definition.

Inference/storage failure degrades current intelligence while allowing telemetry to continue.
At 1,440 predictions or 10,000 intelligence events, writes fail visibly and evidence is retained.
Existing predictions still become eligible for evaluation; event storage must have capacity.
Cloud ACK/compaction and production-sized retention remain deferred. operational_ready stays false.

## Phase 5 optimization additions

SQLite user_version 4 adds immutable optimization policies, runs and transactional outbox.
No policy or monetary rate is auto-provisioned. Requests run synchronously under the repository
lock; bounded registry/candidate size and 100-policy/500-run caps prevent unbounded snapshots.
Infeasible is a recorded domain outcome, not a worker crash. API diagnostics record request
outcomes/duration with existing redaction. Cloud synchronization remains unimplemented.
Optimization state is accessed through the fixed native optimization_request bridge. Runtime
operational_ready remains false: proposals are advisory and every proposal is NOT_AUTHORIZED.

## Phase 6 dispatch additions

SQLite user_version 5 adds durable commands, mutation receipts, event outbox and idempotent
simulator acceptance. The local simulator dispatch worker runs every 0.5 seconds and fails
unfinished commands on restart or an uncertain worker/storage error. Health reports its state.
One active command per facility prevents stacked reductions. The native session has an eight-hour
sensitive-action expiry and fixed simulation-only capabilities. Approval still requires an
explicit local UI decision and reason; no verified user identity is provisioned. No real OT
adapter, physical-write permission or verified savings schema exists in this phase.

## Phase 9 advisory AI

`GRIDFORGE_AI_PROVIDER` defaults to `local`; other values disable the provider visibly.
Optional `GRIDFORGE_AI_KNOWLEDGE_DSN` and `GRIDFORGE_AI_QUERY_DSN` select central reader backends.
The native launcher passes these and the Phase 8 cloud URL/edge token through an explicit
allowlist. It continues to clear all other inherited environment settings. Credentials are
absent from UI DTOs, source citations, query inspectors and diagnostic logs.

Copilot shows provider availability and selected retrieval/query backends. A provider/backend
failure produces a persisted UNAVAILABLE answer without changing core runtime readiness.
Documents cap at 100 immutable revisions, 20,000 characters each; answers cap at 10,000.
Concurrent answer generation is bounded to one request per runtime with an explicit busy error.
Queries cap at 100 output rows from the latest 1,000 scoped rows and a 200 ms execution budget.
SQLite lock waiting caps at 100 ms; central connection establishment caps at two seconds.
No silent truncation is described as a complete facility/billing history.

The local simulation actor now uses stable edge identity so its conversations survive restarts.
Native session credentials remain fresh and expire; production person-level identity is deferred.
